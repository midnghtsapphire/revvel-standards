# Runbook — Companion enrollment

## Windows local companion (intended procedure; no binary exists yet)

1. **Decide the allowlist first.** Create dedicated folders, e.g.
   `C:\Users\<you>\RevvelOps\Inbox` and `...\Staging`. Never allowlist `C:\Windows`,
   `C:\Program Files`, or a user profile root — the companion refuses to start if you do.
2. **Install** the companion as a per-user tray application (no admin rights, no service account).
3. **Enroll** with a one-time pairing code generated by the operator in the control plane. The
   resulting token is stored via Windows DPAPI / Credential Manager, never in a file in this repo.
4. **Confirm outbound-only.** The companion dials the control plane over TLS. Verify no listening
   port was opened (`netstat -ano | findstr LISTENING` should show nothing new for the process).
5. **Leave the command allowlist empty.** Adding entries creates an execution surface; each entry
   needs a documented compensating action and an approval gate.
6. **Test read-only.** Run `local.fs.index_allowlisted` and confirm only metadata and hashes leave the
   machine — never file contents.
7. **Test the local approval prompt.** Every write capability must raise a toast/tray confirmation on
   the machine itself, in addition to control-plane approval.
8. **Deletion is unavailable.** Use `local.fs.move_to_staging` plus retention instead.

Unenrollment: revoke the enrollment id in the control plane, uninstall, and clear the credential
entry. Metadata already indexed remains referenced only by hash in the audit chain.

## Mobile companion (contract only)

There is no default ability to read a phone, and nothing in this repository can observe a device.
Enrollment requires **all three**:

1. **Installed companion app** — user-initiated install from the platform's store or an authorized
   channel.
2. **User-approved OS permissions** — granted per data class in the OS settings and revocable at any
   time. Android and iOS both deny by default; iOS restricts background notification and file access
   far more than Android.
3. **Separate local authorization** — device enrollment with a pairing code plus device biometric
   confirmation, distinct from any cloud OAuth grant.

Operational rules:
- Device-initiated push only. The control plane cannot pull user data from the device.
- Start with `mobile.capture.push_note` and `mobile.approvals.respond` (biometric per approval).
- Leave `mobile.notifications.summarize_optin` and `mobile.files.upload_selected` off; they are
  `unavailable` by default and approval-gated even when enabled.
- `mobile.device.read_arbitrary` is hard-denied and will never be implemented.
- Revoking an OS permission or unenrolling the device disables the capability immediately.
