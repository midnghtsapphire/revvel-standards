# Agent Index — canned searches over a local table, instead of rediscovery

**Status:** design, not built. Nothing in this document exists yet.
**Date:** 2026-08-21
**Problem it solves:** agents spend most of their model budget re-deriving
context that has not changed, which is both the expensive part and the
non-deterministic part.

---

## The observation this comes from

Watch what a persona actually does when it is handed a red check.

1. Work out which workflow produced the check.
2. Work out whether that check is red on `main` too.
3. Work out whether an open WR or PR already covers it.
4. Work out whether this exact symptom has happened before.
5. *Then* decide what to change.

Steps 1–4 are **lookups**. They have one correct answer at any moment, that
answer is the same for every agent that asks, and it does not depend on
judgment. Today each agent rediscovers all four by grepping and reading files,
which costs the most tokens, gives the least reliable result, and produces a
different answer depending on which model happens to be answering.

Step 5 is the only part that needs a model.

The whole design is: **precompute 1–4 into a table, and spend the model only on
5.**

## Why this is the difference between a paid model and a free one

A large model can do 1–5 from a cold start. A 7B local coder cannot — not
because it cannot write the patch, but because it cannot reliably do the
archaeology first.

Give it the answers to 1–4 in the prompt and the remaining task is
*"in this file, at this line, this is wrong, fix it"* — which a small local
model does well. The index is not a performance optimisation. It is the thing
that makes a free local lane viable at all.

| | Today | With the index |
| --- | --- | --- |
| Tokens per task | large — reads many files to orient | small — one query result |
| Same input → same answer | no | yes for steps 1–4 |
| Model needed | paid, large | local coder, ~7B |
| Cost | per call | $0 |

## What it is, concretely

A single SQLite file, `.agent-index/index.db`, **generated** and never
hand-edited. Generated by a plain Node script from things this repo already
has — the workflow files, `DECISIONS.md`, `learnings.md`,
`docs/TOOL_COST_INDEX.md`, and the GitHub API for live PR/check state.

SQLite because it needs no server, no daemon, no credentials, and no network.
It is a file. An agent opens it read-only and runs a named query.

**It is a cache, not a source of truth.** Every row records where it came from,
so a stale or wrong row is traceable to the file or API call that produced it,
and the fix is to regenerate — never to edit the row.

## Tables

Six. Each earns its place by removing a specific rediscovery an agent does
today.

### `workflow_index`

Removes: *"which workflow produces this check, and can it spend money?"*

```sql
CREATE TABLE workflow_index (
  file            TEXT PRIMARY KEY,   -- .github/workflows/foo.yml
  name            TEXT NOT NULL,      -- the `name:` field
  triggers        TEXT NOT NULL,      -- JSON array of live on: keys
  commented_out   TEXT NOT NULL,      -- JSON array of triggers present but commented
  check_names     TEXT NOT NULL,      -- JSON array of job/check names it can post
  reaches_llm     INTEGER NOT NULL,   -- 0/1: require-graph reaches openrouter-routing
  can_bill        INTEGER NOT NULL,   -- 0/1: reaches a paid provider, ungated
  lane_env_ok     INTEGER NOT NULL,   -- 0/1: passes LMSTUDIO_ENDPOINT + gate var
  source_sha      TEXT NOT NULL
);
```

`reaches_llm` is computed by walking `require()` from every `node scripts/*.js`
the workflow runs — the same walk in
`tests/persona-workflows-plumb-the-lanes.test.js`. That walk found **nine**
consumers where hand-grepping found two. It belongs in a table, not in one
test.

### `check_history`

Removes: *"is this red on `main` too, or is it mine?"* — the single most
repeated and most often wrong judgment in this repo.

```sql
CREATE TABLE check_history (
  check_name    TEXT NOT NULL,
  pr_number     INTEGER,              -- NULL for a main-branch run
  sha           TEXT NOT NULL,
  state         TEXT NOT NULL,        -- success | failure | error | pending
  description   TEXT,
  observed_at   TEXT NOT NULL,
  PRIMARY KEY (check_name, sha)
);
```

### `known_failures`

Removes: *"has someone already decided this red check is not worth
diagnosing?"*

Hand-curated, the one table a human writes. Small on purpose.

```sql
CREATE TABLE known_failures (
  check_name    TEXT PRIMARY KEY,
  reason        TEXT NOT NULL,        -- "Vercel account blocked"
  issue         TEXT,                 -- "#17831"
  owner_action  INTEGER NOT NULL,     -- 1 = no agent can fix this
  since         TEXT NOT NULL
);
```

Seeded today with `Vercel – *` (#17831) and `recurseml/analysis` (#17855).
Every agent that has burned tokens diagnosing those would have stopped at one
query.

### `learnings_index`

Removes: *"has this symptom happened before?"* — which `CLAUDE.md` already
instructs every agent to check, by skimming a file that is now thousands of
lines long. An instruction to skim a growing file is not a search.

```sql
CREATE TABLE learnings_index (
  id          INTEGER PRIMARY KEY,
  date        TEXT NOT NULL,
  title       TEXT NOT NULL,
  symptom     TEXT NOT NULL,          -- the observable, in the reporter's words
  paths       TEXT NOT NULL,          -- JSON array of files the entry names
  rule        TEXT,                   -- the one-line rule, where the entry has one
  anchor      TEXT NOT NULL           -- learnings.md heading
);
CREATE VIRTUAL TABLE learnings_fts USING fts5(symptom, title, rule,
                                              content='learnings_index');
```

FTS5 so a symptom string matches without an LLM in the loop.

### `decisions`

Removes: *"is this decision still in force, or was it reversed?"*

`DECISIONS.md` is already a table rendered as markdown. Parsing it into an
actual table makes `reversed_by` a column instead of a regex — the thing
`tests/tool-cost-index-matches-decisions.test.js` currently reimplements.

```sql
CREATE TABLE decisions (
  id           TEXT PRIMARY KEY,      -- D016
  summary      TEXT NOT NULL,
  rationale    TEXT NOT NULL,
  date         TEXT NOT NULL,
  reverses     TEXT,                  -- D014
  reversed_by  TEXT,                  -- filled in on the row it reverses
  workflows    TEXT                   -- JSON array of files it governs
);
```

### `open_work`

Removes: *"is there already a WR or PR for this?"* — the duplicate check
DRAGNET's own instructions require on every single run.

```sql
CREATE TABLE open_work (
  kind        TEXT NOT NULL,          -- issue | pr
  number      INTEGER PRIMARY KEY,
  title       TEXT NOT NULL,
  state       TEXT NOT NULL,
  labels      TEXT NOT NULL,          -- JSON array
  author      TEXT NOT NULL,
  is_draft    INTEGER NOT NULL,
  paths       TEXT,                   -- JSON array of files a PR touches
  observed_at TEXT NOT NULL
);
```

## The canned searches

Named queries with bound parameters. An agent calls a name; it does not write
SQL, and it cannot write SQL — the surface is a fixed list.

| Name | Answers | Replaces |
| --- | --- | --- |
| `check_owner(check_name)` | which workflow posts this check, and can it bill | reading workflow files |
| `is_known_red(check_name)` | is this a known, owner-only failure | rediagnosing Vercel every time |
| `red_on_main(check_name)` | is this red on main too | "is it me?" |
| `prior_incidents(symptom)` | FTS over learnings | "skim learnings.md" |
| `open_work_for(path)` | existing WR/PR touching this file | the duplicate check |
| `decision_in_force(id)` | is this decision current or reversed | D007/D014/D016 confusion |
| `billing_workflows()` | every workflow that can spend | the spend audit, on demand |

Each is one function, returns JSON, and is callable from Node, Python, or the
CLI so every lane can use it.

## What is still the model's job

Deliberately unchanged. The index answers *what is true*; it never answers
*what to do*.

- Reading a stack trace and locating the actual defect
- Writing the patch
- Judging whether a prior incident is genuinely the same, or only looks similar
- Deciding a fix is out of scope and saying so
- Writing the regression test

If the index ever starts recommending fixes, it has become an
unversioned second brain competing with the code, and it should be cut back.

## Refresh

Regenerated by `node scripts/build-agent-index.js`:

- from repo files — instantly, deterministically, no network
- from the GitHub API — for `check_history` and `open_work`

Runs at the top of any agent task, and on `push` to main. **No schedule** — the
cost freeze holds. The repo-only tables cost nothing and take under a second;
only the two API-backed tables need network, and they degrade to "stale, last
observed at X" rather than failing.

`.agent-index/index.db` is gitignored. It is generated, so committing it would
create a second copy of the truth that can disagree with the first.

## How it gets verified

The rule this repo keeps relearning is that a marker nobody checks is
decoration. An index nobody validates is the same thing, one layer deeper.

1. **Every row carries `source_sha` or `observed_at`.** A row that cannot say
   where it came from is a bug.
2. **A test rebuilds the index from the current tree and asserts spot facts** —
   that `recurse-ml.yml` shows `pull_request` in `commented_out` and not in
   `triggers`; that `billing_workflows()` returns the same set the coverage
   test finds. If the index and the tests disagree, the build is wrong.
3. **Mutation check.** Re-enable a trigger in a fixture, rebuild, assert the
   table changed. An index that reports the same answer regardless of input is
   inert.

## Build order

Smallest useful thing first, and each step is independently valuable.

1. `known_failures` + `is_known_red()` — hand-written, ~20 rows, saves the most
   wasted diagnosis immediately, needs no build script.
2. `workflow_index` + `check_owner()` / `billing_workflows()` — pure repo
   parse, no network, replaces the require-graph walk.
3. `learnings_index` + FTS — makes `CLAUDE.md`'s "skim learnings.md" a real
   search.
4. `decisions` — turns the D-reversal regex into a column.
5. `open_work` + `check_history` — the two that need the API; last, because
   they are the only ones that can be stale or fail.

Stopping after step 2 still leaves the repo better off than it is now.

## What this does not fix

Being explicit, so this is not read as a cure.

- **It does not restore repo-surgery capability.** A local 7B coder with a
  perfect index is still a 7B coder. It handles narrow, well-specified edits.
  It will not take "CI is red, go work it out" and succeed.
- **It does not make the fleet autonomous again.** Scheduled runs are frozen.
  The index makes each triggered run cheaper and more repeatable; it does not
  trigger anything.
- **It adds a thing that can be wrong.** A stale index confidently returning
  yesterday's answer is worse than no index, which is why every row carries its
  provenance and why the tests rebuild rather than trust.
